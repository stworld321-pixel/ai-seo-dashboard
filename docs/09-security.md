# Security Architecture

## Secrets (spec §3: "Do NOT store API passwords/secrets in plain text")

- `ENCRYPTION_KEY` (32 bytes, base64) in env; never in the repo.
- `src/server/crypto.ts`: AES-256-GCM. `encrypt(plaintext) → {cipher, iv, tag}` stored in three
  `Bytes` columns. Decryption happens only inside `integrations/*` at call time; decrypted values
  are never logged, never returned by any API route, never placed in React props.
- A `SECRET_FIELDS` redaction list is applied in the logger — any object passing through
  `logger.*` has those keys replaced with `[redacted]`.
- Key rotation: `secretVersion` column + `scripts/rotate-keys.ts` re-encrypts in a transaction.

## AuthN / AuthZ

- Auth.js v5, DB sessions, httpOnly + SameSite=Lax + Secure cookies, 30-day rolling.
- Passwords: argon2id. Optional Google sign-in.
- Authorization is a server-side helper, not middleware-only:
  `requireWebsiteAccess(userId, websiteId, minRole)` runs inside every service function. A route
  can't forget it, because services refuse to run without a resolved actor.
- Roles: OWNER > ADMIN > MEMBER > VIEWER. VIEWER can never create approvals or trigger writes.

## The guard layer (spec §21, §42)

```ts
guard.assertAllowed({ websiteId, action, actor })
```
Resolves the website's `automationLevel`, looks the action up in a static risk table, and either
allows, or creates an `Approval` and throws `APPROVAL_REQUIRED`. Destructive actions
(`page.delete`, `redirect.create`, `url.change`, `canonical.change`, `robots.change`,
`schema.sitewide`, `content.bulk_replace`) are in the table as `ALWAYS_APPROVE` — no level
bypasses them. There is no code path to a CMS delete because no adapter implements one.

## Input & output safety

- Every route body parsed by Zod; unknown keys stripped.
- Prisma parameterized queries only; no raw SQL string interpolation (`$queryRaw` with tagged
  templates where raw is needed).
- Content generated by LLMs is sanitized (DOMPurify server-side) before storage and before CMS
  write — no script tags or event handlers can reach the live site.
- Prompt-injection defense: crawled competitor/page text is passed to the LLM inside a delimited
  `<untrusted_content>` block with an explicit instruction that it is data, never instructions;
  agent tool allowlists mean even a successful injection can't reach a write tool.

## Rate limiting & abuse

- Upstash rate limit: 60 req/min/user on read routes, 10/min on generate routes, 5/min on
  publish. Cron routes require `Authorization: Bearer CRON_SECRET` and are IP-restricted in prod.
- Per-website daily LLM token budget enforced before each generate call.

## Data handling

- GSC/GA4 data is the customer's; scoped by `websiteId` everywhere, deleted on website delete via
  `onDelete: Cascade`.
- Audit trail: `AgentLog` + `Approval` + `ContentVersion` give a complete who/what/when for every
  change that touched a live site.
- Backups: Neon PITR (7 days on free tier); `scripts/export-website.ts` for per-tenant export.

## Compliance-ish guardrails baked in (spec §42)

Never: promise ranking increases (the UI says "estimated additional clicks" with method shown),
generate search volume (we only display GSC impressions), fabricate backlinks or citations (QA
gate 3/4), create doorway pages (gate 1/2 blocks near-duplicates), keyword stuff (gate 5),
mass-produce low-value pages (per-day publish caps + QA thin-content gate), delete content
(no adapter method), or make destructive technical changes unapproved (guard table).
